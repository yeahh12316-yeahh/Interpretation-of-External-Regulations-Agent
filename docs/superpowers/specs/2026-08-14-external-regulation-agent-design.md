# 外规解读agent：产品与技术设计规格

**日期：** 2026-08-14  
**状态：** 用户已确认，进入实施计划  
**产品形态：** 公开访问的静态网页应用，代码托管于私有 GitHub 仓库  
**核心原则：** 原文优先、证据先行、推断明示、人工定稿、数据不出浏览器（模型请求除外）

## 1. 产品目标

“外规解读agent”用于协助金融机构合规人员阅读监管文件，并生成可追溯、可复核、可修订的外规解读成果。

用户输入：

- 监管文件，必填；
- 监管机构发布的官方解读，选填；
- 用户自有的 OpenAI 兼容接口地址、API Key 和模型名称。

系统输出：

- 完整版《外规解读报告》；
- 面向管理层和业务部门的《新规快评》；
- 与每项结论绑定的原文依据、位置和结论类型；
- 可供合规人员确认、修改、删除、补充和退回重分析的复核记录。

本产品不替代法律或合规判断。监管原文完整性、效力状态、生效日期、重大禁止事项和重大机构影响必须由合规人员复核后才能形成“人工定稿版”。

## 2. 范围与边界

### 2.1 本次交付范围

首次可公开使用的版本同时支持：

- 文字型 PDF；
- 扫描 PDF 和图片型 PDF 的浏览器本地 OCR；
- DOCX、TXT 和粘贴文本；
- 监管文件与官方解读的分别上传和来源标记；
- 真实文件解析、结构化监管分析、证据校验、人工复核与修正；
- 完整报告和新规快评两种不同成果；
- DOCX 和 PDF 本地导出；
- 浏览器本地项目保存、恢复、JSON 备份与迁移；
- 用户自带模型接口（BYOK）及连接测试。

### 2.2 明确不包含

- 不抓取或解析监管机构网页链接；
- 不由平台提供共享 API Key；
- 不建设平台业务后端、用户数据库或云端文件存储；
- 不自动判断并宣称监管文件当前有效；
- 不自动对外发布报告；
- 不将 AI 输出标记为“监管机构观点”；
- 不承诺不经人工复核即可用于重大合规决策。

## 3. 信息来源与结论边界

系统只允许使用以下三类信息：

1. **监管原文事实**：来自用户上传的监管文件，是义务、禁止、日期、适用范围和法律表述的第一依据。
2. **官方解读说明**：来自用户上传并明确标记的官方解读，可用于解释政策背景、目标和监管意图，但不得覆盖或改写监管原文。
3. **AI 合理推导**：根据监管原文对金融机构可能影响所作的分析，必须单独标记为“AI 推导”，并绑定推导所依赖的原文条款。

若未上传官方解读，系统仍可解析监管原文，但必须提示“未提供官方解读，政策背景与监管意图仅依据监管原文，不扩展为官方观点”。

每条结论必须属于以下一种状态：

- `regulatory_fact`：监管原文直接事实；
- `official_explanation`：官方解读中的说明；
- `ai_inference`：AI 推导；
- `pending_confirmation`：证据不足或存在歧义，待人工确认；
- `human_judgment`：复核人员新增的判断。

报告生成器不得新增分析事实，只能重组已通过校验或人工确认的结构化结论。

## 4. 用户工作流

界面使用五个连续步骤，每页同时提供“上一步”和明确的“下一步”按钮，左侧流程导航可跳转但不得绕过必要状态校验。

### 4.1 材料上传

- 监管文件上传区始终完整可见，必填；
- 官方解读上传区独立展示，选填；
- 支持拖拽、文件选择和粘贴文本；
- 显示文件名、类型、大小、页数（可识别时）、哈希和来源类别；
- 不允许把官方解读误标成监管原文；
- 用户点击“开始本地解析”后进入解析步骤。

### 4.2 解析与 OCR

- 文字型 PDF 优先抽取文本层；
- 扫描页或低文本密度页自动进入本地 OCR；
- DOCX、TXT 在浏览器内解析；
- 形成页面、条款、段落和坐标锚点；
- 展示解析覆盖率、OCR 页数、低置信度字符、疑似缺页和需人工检查项目；
- 用户可查看解析文本并纠正 OCR 结果；
- 解析失败的页不得静默跳过。

### 4.3 监管分析

- 模型按照固定结构输出监管背景、适用范围、核心要求、禁止事项、时间与过渡期、机构影响和待确认事项；
- 中间结果以卡片和分类页签展示；
- 点击任一结论，右侧证据面板必须动态切换至该结论对应的文件、页码、条款、原文片段及结论类型；
- 点击“查看校验详情”展开该结论的引用匹配、定位结果、强度词检查、推断标记和失败原因；
- 自动证据校验作为后台质量闸门，不再作为独立用户步骤；
- 页面底部提供“进入人工复核”。

### 4.4 人工复核与修正

系统展示全部结论，并优先排列以下事项：

- 证据校验失败或低置信度结论；
- 生效日期、过渡期和适用范围；
- 禁止事项与重大影响；
- AI 推导和存在冲突的官方解读。

每条结论支持：

- 查看原文或查看推导依据；
- 确认；
- 修改；
- 删除；
- 新增人工判断；
- 退回 AI 重新分析，并填写原因和分析范围。

右侧证据面板随当前复核项同步切换。系统保留 AI 原始版本、人工修订版本、修改人、时间和理由，不覆盖历史记录。

只有合规人员完成必审项后，项目状态才能变为“人工定稿”。未完成时可以预览草稿，但导出文件必须显著标记“AI 草稿，未经人工复核”。

### 4.5 报告生成与导出

用户可在“外规解读报告”和“新规快评”之间切换并预览完整内容。两者共享同一套已复核结构化数据，但采用不同的信息结构和篇幅，不能只替换标题。

导出在浏览器内完成，支持 DOCX 和 PDF。导出前显示成果类型、版本状态、生成时间、来源清单和人工复核状态。

## 5. 两类成果结构

### 5.1 外规解读报告

1. 管理摘要；
2. 文件基本信息、发文机关、文号、发布日期及效力待复核提示；
3. 监管背景与政策目标；
4. 适用对象和适用范围；
5. 核心要求逐项解读；
6. 禁止事项和监管红线；
7. 生效日期、实施安排与过渡期；
8. 对金融机构的主要影响，按治理、制度、流程、系统、数据、人员和报告维度展开；
9. 建议行动及优先级，明确标记为 AI 推导或人工判断；
10. 待确认事项和风险提示；
11. 原文证据索引与人工修订留痕。

### 5.2 新规快评

1. 一句话结论；
2. 新规为什么重要；
3. 最值得关注的三至五项变化；
4. 禁止事项和不可触碰红线；
5. 关键日期、过渡期和紧迫程度；
6. 主要受影响机构、业务和部门；
7. 近期行动清单；
8. 重要限制、待确认事项和来源说明。

快评应控制为短篇管理层阅读材料，使用短段落和要点；完整报告则保留逐项条款、影响逻辑和证据附录。

## 6. 七项内部能力（skills）

### Skill 1：文件解析与原文定位

将上传文件转为带稳定来源锚点的文本单元。输出文件 ID、页面、条款、段落、坐标、文本和 OCR 置信度。

### Skill 2：文件身份、效力与监管背景识别

提取发文机关、文号、文件名称、发布日期、明示的生效/废止信息和政策背景。无法从材料确认的效力状态必须标记待人工复核。

### Skill 3：条款原子化分析

把复合条款拆分为最小可执行要求，识别主体、行为、对象、强度、条件、频率、期限和例外。

### Skill 4：重点事项归纳

从原子条款中归纳核心要求、禁止事项、生效日期、实施安排和过渡期，不改变“应当、不得、可以”等监管强度。

### Skill 5：金融机构影响分析

将监管要求映射至治理、制度、流程、系统、数据、人员和报告维度。所有影响结论均作为 AI 推导，除非材料直接明示。

### Skill 6：证据与一致性校验

反向检索每项引用，检查原文一致性、页码/条款定位、强度词、日期、结论类型、引用完整性和推导链。失败项目转入人工复核，不进入自动定稿。

### Skill 7：报告编排

仅基于校验通过或人工确认的数据生成两类报告，保留来源标签、待确认事项和复核状态。

人工复核是产品工作流的最终质量闸门，不作为第八项 AI skill。

## 7. 系统架构

系统采用纯静态前端架构，可由 Vercel 等静态托管服务从私有 GitHub 仓库部署为公开网址。

### 7.1 浏览器端模块

- `FileIntake`：文件选择、类型检查、哈希和来源分类；
- `DocumentParser`：PDF 文本抽取、DOCX/TXT 解析和页结构识别；
- `OcrPipeline`：扫描页检测、本地 OCR、置信度与纠错；
- `SourceAnchorStore`：稳定来源 ID 和页码、条款、段落、坐标索引；
- `ModelGateway`：OpenAI 兼容请求、连接测试、超时、重试和结构化输出解析；
- `SkillOrchestrator`：按七项内部能力执行、分段处理、合并结果；
- `EvidenceValidator`：确定性引用反查和规则校验；
- `ReviewStore`：人工确认、修订、退回和版本记录；
- `ReportRenderer`：两种成果预览、DOCX/PDF 生成；
- `ProjectStore`：IndexedDB 项目保存、恢复和 JSON 导入导出。

各模块通过明确的数据结构交互；界面组件不得直接拼接模型自由文本作为最终报告。

### 7.2 模型接口

用户在“接口设置”中填写：

- API Base URL；
- API Key；
- 模型名称；
- 可选请求参数，例如温度和最大输出长度。

系统只支持声明为 OpenAI 兼容的 HTTPS 接口。连接测试需要验证网络可达、CORS、鉴权和模型响应格式。接口必须允许浏览器跨域请求；若服务商不允许 CORS，纯前端模式无法绕过，界面应给出明确错误而非无限加载。

API Key 只存在内存或 `sessionStorage`，关闭标签页/浏览器会话后清除；不写入 IndexedDB、项目 JSON、日志、URL、错误报告或导出文件。

### 7.3 部署

- 私有 GitHub 仓库保存源代码；
- 静态托管平台连接私有仓库并构建前端；
- 生产网址公开访问；
- 仓库私有不等于网站私有，访问权限由托管配置决定；
- 构建产物中不得包含任何 API Key、测试密钥、上传样本或真实监管项目数据；
- 发布流程必须包含依赖锁定、自动测试、构建检查和敏感信息扫描。

## 8. 核心数据结构

### 8.1 原文单元 `SourceUnit`

- `sourceId`：文件级稳定 ID；
- `sourceType`：`regulation` 或 `official_interpretation`；
- `fileName`、`fileHash`；
- `page`、`article`、`paragraphIndex`；
- `boundingBox`：可用时记录；
- `text`；
- `extractionMethod`：文本层、OCR、DOCX 或 TXT；
- `confidence`；
- `reviewStatus`。

### 8.2 结构化结论 `Finding`

- `findingId`；
- `category`：背景、适用范围、核心要求、禁止事项、时间、影响或待确认；
- `statement`；
- `claimType`；
- `subject`、`action`、`object`、`strength`、`condition`、`frequency`、`deadline`、`exception`；
- `sourceAnchors[]`；
- `inferenceParents[]`；
- `validationResults[]`；
- `confidence`；
- `reviewStatus`；
- `revisionHistory[]`。

### 8.3 项目状态 `Project`

- 项目基本信息和创建时间；
- 文件元数据及是否选择本地保存原文件；
- 解析版本、模型配置（不含 API Key）和模型响应版本；
- 全部原文单元和结构化结论；
- 人工复核记录；
- 报告快照和导出记录；
- 当前步骤和状态：解析中、AI 草稿、待复核、人工定稿或失败。

## 9. 数据保存与隐私

采用浏览器本地保存，不建设平台数据后端。

- API Key：仅当前会话保存；
- API Base URL、模型名称和非敏感偏好：经用户选择后可本地保存；
- 解析文本、分析结果、复核记录和报告：保存在 IndexedDB；
- 原始上传文件：默认只在当前内存中使用，不长期保存；用户明确选择后才写入 IndexedDB；
- 项目备份：支持导出和导入 JSON，API Key 永不包含其中；
- 清除项目：提供按项目删除和清空本地数据功能，并在执行前二次确认；
- 模型请求：上传文本会发送至用户配置的第三方模型接口，界面必须在首次调用前明确告知数据流向。

“数据不出浏览器”特指平台不收集数据；用户调用模型时，相关文本会发送到用户自行选择的模型服务商，应在隐私提示中明确区分。

## 10. 准确性与防幻觉机制

### 10.1 运行时质量闸门

- 先解析原文并生成来源锚点，再允许模型分析；
- 模型必须返回符合 JSON Schema 的结构化数据；
- 所有监管事实必须绑定至少一个监管原文锚点；
- 所有官方解释必须绑定官方解读锚点；
- 所有 AI 推导必须绑定一个或多个已验证的上游结论；
- 引用文字必须能在标准化原文中反向检索；
- “应当、必须、不得、可以”等强度词不得被模型自行升级或降级；
- 日期、数字、比例、机构名称和例外条件执行专项校验；
- 无证据结论不得进入报告正文，转为待确认事项；
- 报告编排阶段禁止调用模型补充新事实；
- 重大事项必须人工确认后才能形成定稿。

### 10.2 单次项目展示的质量指标

系统展示可计算指标，不显示模型自报的笼统“准确率”：

- 文件页数与成功解析页数；
- OCR 页数、低置信度页数和人工纠错数量；
- 原文条款/段落覆盖情况；
- 结论总数、引用覆盖率和引用反查通过率；
- 无依据结论数；
- AI 推导标记覆盖率；
- 待人工确认数量与重大事项完成率；
- 人工修改、删除和退回数量。

最终定稿要求：事实性结论引用覆盖率 100%、引用反查通过率 100%、无依据结论数为 0、AI 推导标记覆盖率 100%、必审事项完成率 100%。未达到时只能导出带显著水印的 AI 草稿。

### 10.3 产品发布前基准评测

建立由合规人员标注的测试集，覆盖不同监管机构、文件结构、文字 PDF、扫描 PDF、表格、附件、长文件和存在官方解读/无官方解读的情况。发布门槛为：

- 重大核心要求、禁止事项、关键日期和过渡期的精确率与召回率均不低于 95%；
- 全部原子化要求的精确率不低于 90%，召回率不低于 85%；
- 已生成事实结论的引用有效率为 100%；
- 未标记的 AI 推导为 0；
- 在专家标注的基准样本中，重大事项遗漏数为 0；
- OCR 关键字段字符准确率不低于 99%，低于阈值的页面必须进入人工检查。

这些指标只用于评估已测试语料和版本，不对未知文件作绝对正确率承诺。每次更换模型、提示词、解析器或 OCR 引擎后必须重新运行基准评测。

## 11. 异常处理

- 文件类型或大小不支持：在上传阶段阻止并说明原因；
- 加密、损坏或无可读内容的文件：停止解析并提示用户更换文件；
- OCR 资源加载失败：保留可解析内容，明确列出未解析页面，不继续生成定稿；
- 模型连接失败：区分 URL、CORS、鉴权、模型不存在、限流、超时和响应格式错误；
- 模型输出不符合 Schema：自动进行有限次数的格式修复，仍失败则保留错误详情并允许重试；
- 长文件超出上下文：按条款和页面分块，保留重叠上下文，合并后进行去重和交叉校验；
- 来源冲突：监管原文优先，官方解读冲突项标记待确认；
- 页面刷新或意外关闭：从 IndexedDB 恢复最近已完成状态，不保存 API Key；
- 导出失败：保留报告预览，显示失败原因并允许重新导出。

所有错误不得以空白页面、无响应按钮或虚假成功提示呈现。

## 12. 界面与品牌规范

- 产品名称统一为“外规解读agent”；
- 经品牌授权后，在产品名称上方使用正式 Deloitte 标识；开发阶段可使用文字占位，不把非授权标识打包发布；
- 主背景为白色，导航为黑色，德勤绿 `#86BC25` 只用于当前步骤、关键按钮、选中状态和少量强调；
- 正文字号适配网页阅读，步骤文字不得大于产品名称；
- 卡片、上传区、按钮和正文之间保留适当留白；
- 上传区在常见桌面宽度和窄屏下不得被右侧证据栏遮挡；
- 所有交互元素具有 hover、focus、disabled、loading、success 和 error 状态；
- 支持键盘操作、清晰焦点、语义标签和足够的颜色对比度；
- 右侧证据面板在空间不足时改为抽屉或下方区域，而不是压缩主内容至不可用。

## 13. 验收标准

### 13.1 功能验收

- 用户可以上传真实监管文件并完整走通五步流程；
- 文字 PDF、扫描 PDF、DOCX 和 TXT 均有可复现测试样本；
- 任意分析或复核条目被点击时，右侧证据随条目正确变化；
- “查看校验详情”“查看原文”“查看依据”“修改”“确认”“删除”“新增人工判断”和“退回 AI 重新分析”均执行真实操作；
- 人工修订保留 AI 原版与修订留痕；
- 两类报告结构和内容粒度明显不同；
- DOCX/PDF 可以下载、打开且内容与预览一致；
- 无 API Key、解析失败或校验未通过时，按钮状态和错误提示正确；
- 项目可以在刷新后恢复，JSON 可以导出后重新导入；
- API Key 不出现在持久化、日志、URL、报告或备份中。

### 13.2 非功能验收

- 生产构建无白屏、未捕获异常和关键控制台错误；
- 首屏、核心交互和长文件处理具有明确进度与可取消机制；
- 常见桌面分辨率和窄屏布局可用；
- 关键流程具备单元、集成、端到端和故障注入测试；
- 发布前通过依赖、敏感信息和静态资源路径检查；
- 实际公开网址完成一次从上传到导出的生产环境冒烟测试。

## 14. 成功定义

产品成功不是“生成了一段看起来合理的文字”，而是：用户能够使用自己上传的材料和自己的模型接口，完成一次可追溯的外规分析；每项重要结论都能回到原文；AI 推导和事实不混淆；合规人员可以修订并留下记录；最终形成结构不同、可真实导出的解读报告和新规快评，同时平台不持有用户的 API Key 和项目数据。
